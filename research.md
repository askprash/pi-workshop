# Research: security boundaries for agent tools/extensions

## Summary
Prior art consistently treats model-callable tools, extension commands, and local subprocess execution as high-risk surfaces that need host-enforced policy, not model promises or UI naming conventions. A defensible split is not “slash command = human, tool = model”; it is restricted default capabilities plus explicit, parameter-bound user consent/confirmation for privilege elevation, with OS/process containment for any spawned code and honest documentation that artifact placement is not sandboxing.

## Findings
1. **MCP’s own security model assumes tools can be arbitrary code execution and require explicit consent.** The MCP spec says tools are “functions for the AI model to execute,” that MCP enables “arbitrary data access and code execution paths,” and that hosts must obtain explicit user consent before invoking any tool; it also warns that tool descriptions/annotations are untrusted unless from a trusted server. This supports keeping model-callable schemas narrowly scoped and not relying on descriptions as a security boundary. [MCP specification](https://modelcontextprotocol.org/specification/2025-11-25)

2. **Local MCP/server startup commands are treated as dangerous even before the model uses them.** MCP security best practices say one-click local MCP server configuration must show the exact command, identify it as potentially dangerous code execution, require explicit approval, warn that servers run with the same privileges as the client, and should use sandboxing/restricted filesystem/network access. This is directly relevant to subprocess spawning by an extension. [MCP Security Best Practices](https://modelcontextprotocol.org/specification/2025-11-25/basic/security_best_practices)

3. **Least privilege and progressive elevation are preferred over broad “safe mode” claims.** MCP best practices recommend minimal initial scopes, targeted elevation when privileged operations are first attempted, avoiding wildcard/omnibus scopes, and logging elevation events. For workshop modes, project config should not silently expand privileges; elevation should be explicit, reviewable, and auditable. [MCP Security Best Practices](https://modelcontextprotocol.org/specification/2025-11-25/basic/security_best_practices)

4. **VS Code does not treat commands as inherently user-originated.** VS Code commands can be invoked programmatically by other extensions, from UI, keybindings, or command URIs; command URIs embedded in Markdown/webviews can execute commands and require `isTrusted`, with guidance to sanitize so only expected command URIs run. This undercuts any assumption that a command handler can infer “human typed this” solely from the command path. [VS Code Commands](https://code.visualstudio.com/api/extension-guides/command)

5. **VS Code Workspace Trust is prior art for gating code execution from untrusted project content.** The extension guide says malicious workspace contents/settings can influence an extension, especially when settings become CLI flags or workspace code/dependencies are executed. It recommends disabling/hiding trust-sensitive features in Restricted Mode and also blocking execution in code because a command can still be called even if hidden in UI. [Workspace Trust Extension Guide](https://code.visualstudio.com/api/extension-guides/workspace-trust)

6. **Extension runtime permissions are ambient unless the host adds controls.** VS Code documents that extensions run with the same permissions as VS Code and can read/write files, make network requests, run external processes, and modify workspace settings. Marketplace scanning/publisher trust are supply-chain signals, not a runtime sandbox. This is useful framing for “artifact-contained, not sandboxed”: containment of outputs is not containment of process authority. [VS Code Extension Runtime Security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security)

7. **OWASP agent guidance explicitly separates tool policy from model behavior.** OWASP recommends minimum required tools, per-tool read/write/resource scoping, separate tool sets for trust levels, explicit authorization for sensitive operations, human-in-the-loop for high-impact actions, action previews, audit trails, and structured adversarial tests for tool misuse, privilege escalation, approval bypass, data exfiltration, and multi-agent chaining. It says not to give agents unrestricted tools, not to allow arbitrary code without sandboxing, and not to rely solely on model output for authorization decisions. [OWASP AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

8. **Claude Code is a concrete precedent for read-only-by-default plus permission rules.** Claude Code documents read-only operations as default, with approvals for Bash/file modifications, deny/ask/allow rules where deny wins, scoped Bash/file/WebFetch/MCP/subagent permissions, symlink-aware path checks, and managed settings that can prevent project/user config from loosening policy. It also states permissions and sandboxing are complementary: permissions decide tool access; sandboxing gives OS-level enforcement for Bash/child processes. [Claude Code permissions](https://code.claude.com/docs/en/permissions)

9. **Claude Code security docs treat prompts and auto-approval as insufficient controls.** Anthropic documents explicit approval for bash, write confinement to project scope, trust verification for first-time codebases and new MCP servers, fail-closed command matching, command injection detection, network request approval, separate context windows for web fetches, and recommends VMs/dev containers for additional isolation. This is strong prior art against “beta” language replacing enforcement. [Claude Code security](https://code.claude.com/docs/en/security)

10. **OpenAI computer-use guidance emphasizes isolated execution and direct-user-intent boundaries.** OpenAI recommends running browser/computer tools in an isolated browser/container/VM, stripping inherited environment where possible, domain/action allowlists, and human-in-the-loop for high-impact/destructive/authenticated/external actions. It explicitly says third-party/on-screen/tool-output content is untrusted and should not count as user permission; confirmation should happen at the point of risk. [OpenAI Computer Use](https://developers.openai.com/api/docs/guides/tools-computer-use)

11. **Nonce-gated privileged/scratch modes need more than a nonce.** OWASP recommends binding approval to exact action parameters, actor, target resource, timestamp and expiry, using short-lived authorization artifacts, replay protection, and fail-closed validation. For prototype/scratch mode, a nonce/TTL can be an authorization artifact, but it should not be presented as sandboxing; it must be parameter/path-bound, non-replayable, logged, revocable, and paired with process/filesystem controls. [OWASP AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

12. **Multi-agent/subagent delegation is a separate trust boundary.** OWASP calls out multi-agent chaining risks and recommends signed/validated inter-agent communication, recipient/message allowlists, circuit breakers, and preventing privilege escalation through chains. Claude Code exposes explicit `Agent(AgentName)` permission rules. This supports avoiding mutable global subagents with broad write/bash permissions in any “public safe” mode. [OWASP AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html), [Claude Code permissions](https://code.claude.com/docs/en/permissions)

## Gaps
- No single standard cleanly defines “slash command” provenance for Pi-style extensions; VS Code prior art suggests commands are not a reliable human-origin boundary unless the host provides provenance and confirmation APIs.
- Need implementation-specific review of Pi extension APIs: whether extension-injected user messages can invoke slash commands, whether command handlers receive provenance, and whether confirmations are host-enforced or model-mediated.
- Need OS-specific containment decisions for macOS/Linux: sandbox-exec/Seatbelt limitations, containers, chroot/bubblewrap/firejail, devcontainers, env scrubbing, cwd/path/symlink checks, network egress policy, and process-tree cleanup.
